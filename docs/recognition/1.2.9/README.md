## 实现与语义

四入口继续使用同一个 `PickupRecognitionCore`。原来在提取时直接丢弃候选，现改为收集完整观察、统一分类、处理替代/备选关系、投影可用候选。每条观察保留规则、规范化 UTF-16 范围和明确决策：可用、需核对、排除及原因。遮挡或缺失替代码保留未处理状态；被替代/明确其他用途的数字保留排除证据。诊断回放输出这些证据，App 不新增原文或诊断持久化。

`Notification.unresolved`表示缺失/不可用项；`requiresReview`表示候选仍可在核对页处理。直接文字和自动路径跳过待核对项并保留部分结果提示；图片/分享将候选交给既有核对模型。两种状态分开，用户更正截断码后不会残留一条虚假的“未识别通知”提示。既有低置信/缺地点普通候选默认选择策略保留，明确风险继续要求核对或更正。

本轮修正以下已复现约束：

| 输入关系 | 结果 |
| --- | --- |
| 尾号、紧凑日期、客服电话分机出现在到件通知 | 识别其用途，不能作为无标签取件码自动保存 |
| 收件人/收件地址与明确取件码同行 | 排除范围止于字段边界，保留真实取件码 |
| 取件码使用 `【】`、`[]` 等引用 | 不把码当成发送方签名拆块 |
| 全角星号或其他明确遮挡 | 保留不可用状态，不保存完整码的前缀 |
| `取件码1234，更正为56****` | 旧码被替代，新码不可用，禁止继续保存旧码 |
| 修改营业时间、日期、地址 | 不作为取件码替代关系；保留原码 |
| `取件码1234、56****、9012` | 保留 1234、9012，并提示有未处理项 |

存储格式、既有记录、去重身份、队列版本与 OCR 字符策略未改；不猜测 O/0 等字符，不重算旧数据。新增观察只用于当前解析与开发诊断。

## 固定验收入口

```sh
bash scripts/check_recognition.sh /tmp/shouxia-recognition-check
```

命令先运行主机逻辑/存储测试，再编译实际 Swift 源码，执行四入口断言回放；任何断言失败返回非零退出码。直接调试可运行：

```sh
python3 scripts/check_pickup_recognition.py --output /tmp/shouxia-recognition-check
bash scripts/replay_pickup_samples.sh docs/recognition/1.2.9/contracts.jsonl
```

- 研究样本使用已有字段标注，排除只有结构的 T05 与码真值不明的 C14；T06 仅检查手动入口。C22 的详细地点只用于有布局证据的图片入口。品牌沿用“明确承运商优先，否则取件服务”的历史展示合同，仅将兔喜生活/快宝驿站映射到词库中已有规范名；不改变角色定义。
- 1.2.8 的 30 条输入继续检查正常收码；电话同形候选可供核对，但不能默认选中或统计成正常接受。
- 原 7 条复核输入沿用原有标注要求；新增关系合同明确代码序列、遗漏计数或拒绝结果。
- 135 条由三种码、三种标签、五种引用方式和三种同行字段组合产生的变体，验证代码和完整性不被格式/干扰字段改变；它们属于同一家族，不能按 135 个独立模板计数。
- 失败状态、部分完成、核对状态、码、地点及兼容品牌字段分别断言。脚本输出各字段检查数和失败数；不是用测试数量表示准确率。

原研究/1.2.7/1.2.8 的样本、标注和回放文件没有覆盖。变更验收预期必须记录业务理由，禁止从新输出自动更新“正确答案”。`--source-root`可对隔离的历史源码快照执行同一组验收。

## 验证层与剩余边界

实际结果及六项解析源码哈希见 [validation.json](validation.json)。本轮执行主机测试、断言回放及 generic iOS Simulator Debug `build-for-testing`；没有启动 App、Simulator、浏览器或手机 UI。

已积累的研究与修复输入均已参与开发；新增变体也是构造数据。检查通过证明这些固定合同满足，不能证明线上总体准确率、所有未知模板或真实 OCR 正确率。公开资料查找未形成新的、带完整真值的独立真实通知集，本轮不虚构留出集。

后续真实通知应先独立标注，再验证码、地点、错误接受、漏识别、需核对及部分完成；按模板家族保留验证边界。某个样本一旦用于调规则，就转为回归样本，不能继续当未见模板。真机原图、自动收码、核对保存及旧系统运行仍待验收。
