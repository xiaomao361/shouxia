# 取件码、地点与快递角色：研究结论及实现依据

## 结论与证据范围

现有 Apple Vision 路线可以继续；第一轮改进应落在本地解析的**通知边界、候选数字角色、码与地点/品牌的对应关系**。公开材料确实包含没有“取件码”标签的凭码句式、字母开头码、地点中带短横线门牌、同句服务名与承运商。无需建设全国站点库，也没有证据支持此时必须训练新模型。

本轮完成搜索、正文读取、三张公开图片目视核验、政府 PDF 第1页核验、原生 Swift 规则回放和一次三图 macOS Vision 探针。详细数据见 [样本表](SAMPLES.md)、[来源索引](SOURCES.md) 和 [回放表](BASELINE.md)。所有建议都是实施候选，未修改或验证新算法。

核心只含：取件码、取件地点、承运公司/取件服务及其对应关系。时间、期限、状态只在原文中作为排除干扰或避免错误关联的证据，不新增这些产品字段。运行时不调用外部大模型、决策模型、地图查询或快递查询服务，不依赖 Apple Intelligence。

来源的当前可访问性、短信是否完整、字段是否可判定是三个独立维度。R05是**文本无值**，R07是**来源掩码**，T04是**模板占位符**，C14是**无法核实相似字符**；它们不共用一个“没识别到”的研究标签。

S22（厦门大学后勤）和 S23（邮政采购）分别支持多承运商共站、柜方发码与承运商投件的角色区别。它们没有短信原文，不能用于虚增模板覆盖。便利店有 S24 报道，门卫室缺少完整可核验通知；C16/C17是构造用例，不能冒充已采到真实案例。

**不能夸大的问题：** `platform`目前是混合品牌标签，界面也直接显示该字符串，没有明确标题“承运公司”。所以R04显示菜鸟不能直接判为“韵达被识别错”；它证明了当前契约不足以同时表达服务与承运商。C06第二条却被赋予完全无关的菜鸟，则属于跨通知串配。C17已经能正确解析“存放在…门卫室”，因此不能说当前完全不支持门卫室。

## 可落地的本地算法

### 1. 保留证据，再做规范化

把输入表示成原文、规范化文本和原文跨度映射。OCR额外保留完整矩形、候选字符串、置信度、图像/行标识；目前只留minX/midY和top1会丢掉列宽、高度和字符替代证据。它们可先作为临时解析结构，无需迁移持久数据模型。

- 对数字、ASCII字母、冒号、短横线做兼容宽度规范化；不要无差别改变地点的所有符号或删除全部空白。
- 合并码内空白/横线只在候选跨度里做；保留前导零、字母、段数。多通知之间不能先全文去换行。
- 同块、相邻行、列对齐且明显被截断时才连接标签或码（O03/C11）。若连与不连都形成合理候选，保留歧义。
- 括号/引号可以围住标签和值；`829***`和`XX`标为掩码/占位，不截短成829或XX。
- O/0、I/1、S/5、B/8不全局替换。只有OCR备选或原图可验证时再比较；C14没有答案，不能把看起来像数字的串自动改正。

### 2. 通知分段必须先于字段绑定

纯文本按新签名、重复独立通知句、段落分隔、重复完整“地点+码”组合产生分段候选；普通OCR换行不是新通知。同一句“2个包裹…取货码A、B”留在同块（C05）。通知签名与App页面导航标题分开，不把“淘宝”页面顶栏当所有包裹的承运商。

图片利用行高、水平重叠、列对齐和纵向间隔建立局部行簇；先在每个行簇内读取。阈值按中位行高归一化，并由真实版式集校准，不能仅把当前±9行改成另一个固定行数。两列标签值按同一横带和同列续行绑定（S13/C22）；三卡片只在各卡内取品牌/地点（S14）。

存在两个合理分段时输出待确认的候选组，不允许为每个码盲取“附近分数最高站名”。新通知边界是硬限制。上一条有地点、下一条没有地点时，下一条仍缺失（C21）。

### 3. 候选生成与数字角色分析

候选优先级：明确码标签 → 带领取动作的“凭…到/至…取”“凭…来取” → 同块分离标签和值 → 用户明确分享/粘贴的整串裸码。连续数字、字母数字、两到多段短横线仅是形状，形状本身不证明角色。

先标记每个数字跨度的可能角色：电话号码、手机尾号、运单及运单尾号、日期/钟点、数量、门牌/楼栋/柜号/格口、费用、URL、验证码。分析候选左右两侧，尤其后置说明“2635为手机尾号”（C20）。排除应作用于数字跨度，而非整行出现“电话”就丢弃同一行的取件码（R02/C16）。

规则顺序应体现冲突：

1. 掩码、占位、与长数字/字母串相接的截断候选不得成为完整码。
2. 有明确登录/支付/联系方式/房号角色，且没有领取凭证语义的数字不采纳。
3. 明确“取件码A-1-26-11”时，26是码内成分，日期形状不能覆盖明确证据（T06/C26）。
4. “凭手机尾号取件”确实是领取凭证，但与独立取件码的业务含义不同（C02）。本轮标为需确认，不默认改变现有码字段含义；后续实施若要自动接受，先明确产品语义。
5. 列表每个续项也需角色核验；下一通知、地址开始、后置角色解释都会结束列表。

### 4. 可解释排序和拒绝机制

先按硬约束去除非法跨度，再对其余候选分级。建议最初使用有序证据等级，避免未经标定就给“92%置信度”：

|证据|影响|
|---|---|
|同块明确标签直接绑定完整码|强正向|
|同块明确凭码领取句式|强正向；不要求必须有“取件码”三个字|
|空间上同列标签-值、无竞争值|正向，但需保留版式证据|
|只有合法数字形状/已知品牌|弱正向，单独不足以确定|
|电话/房号/登录码等独立角色|排除或强冲突|
|越过通知边界/候选截断/来源掩码|禁止确认为完整字段|
|同块两套互斥码、候选替换字符、两处同等地点|待确认|

每个结果带rule ID、原文跨度、block ID、正/负证据。OCR字符置信度与语义可靠性分开。强标签且OCR高置信度仍可能绑定手机号（C09），地点非空也可能来自别的通知（C21）。如改用加权分数，权重与第一/第二候选分差必须由开发集确定、在冻结留出集检查，不能在本报告臆定阈值或承诺准确率。

### 5. 地点是带边界的短语，不是关键词命中行

起点包括同块明确“取件地址/地点”、包裹到达/存放句、“凭码到/至/前往”的介词宾语；终点包括领取动作、联络信息、下个字段、通知边界和中英文标点。识别“包裹到…”而不只“已到…”。“已到”本身也可能只是运输节点，需与同块领取动作或码绑定，不能把轨迹中转站当目的地。

保留地点内数字、括号、门牌后缀（R03、C05）；不能为了避开数字误码而删掉门牌。“1号柜”可作为部分地点保留，不能凭常用站点补成具体小区。去除签名、主语、提醒语、电话之后再判断边界；不能只清开头标点而留下“中通】已到”。

驿站/柜/代收点/超市等后缀只作加分。无关键词的“绿色果园”在明确领取关系中仍可成为地点（R06），但无明确关系的商品店铺名不应被采纳。普通店、便利店、门卫室、前台需自然句式支持，不另建全国站名数据库。

### 6. 承运商与取件服务分开判，再决定旧字段怎么展示

在解析内部保留两个可空角色：carrier与pickupService；购物平台或App标题另作上下文。用通知中的局部关系认定：圆通快递包裹、韵达…包裹是承运证据；妈妈驿站签名、丰巢柜是服务证据。不能因“妈妈驿站属圆通”就把该站所有包裹标圆通，也不凭未经验证的运单前缀推断公司。

内部角色分离不等于本轮要求迁移`PickupRecord`。先用研究适配器保留证据，继续现有持久化结构即可探索。若旧`platform`只能显示一个字符串，必须明确其含义与冲突处理；不要通过固定品牌顺序丢掉更相关证据，也不要在历史数据上回填推断承运商。是否增加双角色展示/字段是后续实施前的产品决策。

### 7. 组装、去重与缺失

把同一通知块内的码、地点、角色组装为有出处的一组；明确多码列表可共享地点。地点缺失或品牌不明确时保留nil/待确认，不借另一通知的信息来“补全”。有两个可能地点时保留候选，不把一个任意选中的地点当高置信度。

码只在同通知、同上下文的重复观察中去重。不同地点相同码不能直接消失（C08）。跨截图重叠需有通知结构、地点/角色、相对布局等一致证据才合并；不确定时让用户区分。当前`extractLabelledCodes`、图片deduplicated、batch merger、分享items唯一约束及selectedCodes都依赖code身份，改动需共同验证。先做会话内候选身份即可研究，无需立即改历史存储键。

内部结果至少区分：确定、待确认、字段缺失、无可用码、掩码/占位、OCR引擎失败、输入不可读。这是解析结果状态，不是快件“待取/到期”业务状态。部分通知成功时保留成功部分并指出未解决块，不能吞掉错误或伪装全部完成。

## Apple OCR 配置建议

现有`.accurate`、中文优先、关闭语言纠正是合理起点。[Apple WWDC19](https://developer.apple.com/videos/play/wwdc2019/234/)说明文本识别在设备上执行，并提示自然语言纠正可能损伤序列码；无需接入Apple Intelligence。

[Apple WWDC21](https://developer.apple.com/videos/play/wwdc2021/10041/)建议查询给定请求支持的语言，且语言顺序影响accurate识别。后续记录实际OS/设备、Vision revision、支持语言和请求配置，避免系统变化被误当规则变化。项目当前部署目标iOS16，方案继续基于`VNRecognizeTextRequest`，不引入只为新SDK的替换API。

- 留完整boundingBox，并只在难例附近请求有限备选（如top3实验）；候选数是性能实验值，不是已证明最优。
- 先保留当前关闭纠正的码通道；只有真实地点错字样本证明有益时，再比较局部地点OCR开启纠正的收益和耗时。不要默认双跑整图。
- 不设置会滤掉小字体地址的较高minimumTextHeight。低清、裁切、压缩和深色主题分别记录。
- 截图通常无须文档透视矫正；拍照类素材另分组，不能全图锐化/二值化后声称必然更准确。
- 记录每图耗时、峰值内存、行数和引擎失败。5图分享应验证串行/受限并发及扩展内存，但本轮没有授权实现或运行扩展UI。

## 验证设计：按家族隔离，按字段和对应关系计数

本次44条全部用于观察和设计，因此统一标`development_observed`。不能现在挑其中一部分标为“独立留出”再宣称泛化。后续先冻结规则，再由用户新错例或新的独立采集者补充未参与开发的模板家族。样本量不足时用原始计数与逐例结果，不给虚假准确率。

去重/划分以**模板骨架、站点系统、来源关联和派生链**为单位。R01/R03属于妈妈驿站同骨架；C06/C07属于同通知断行变体；T06/C26同格式派生；O03/C10同标签断行机制。换数字、换地名、换OCR噪声不能跨开发与留出。家族是初步人工标注，扩库时合并近似家族；合成集单列，不能稀释真实失败。

分两层验证：人工正确转录 → 解析，以及原图 → Vision → 解析。前者定位规则，后者包含OCR与版式错误。原图真值由人独立标；禁止把当前程序输出当正确答案。缺字的截图可标partial，而不是要求算法凭空补全。

|维度|应记录的四类结果|比较规则|
|---|---|---|
|码|正确 / 误提取 / 漏提取 / 待确认|规范化后整码精确匹配；替换错码同时贡献FP与FN；保留多重集合，不能用Set抹掉不同通知同码|
|地点|正确 / 误提取 / 漏提取 / 待确认|先评字符边界，再评语义可用性；原文部分地点单列，不以“含驿站”通过|
|承运商与服务|每个角色分别四类|用所属通知与证据跨度认定；不从站点所属公司或购物平台反推|
|整组对应|全组正确 / 错配 / 缺组 / 待确认|需要码、地点和角色属于同一通知；各字段分别出现不算整组正确|

附加：负例误提取数、同码多地点保留数、多通知漏块数、自动确定错误数、待确认率、输入拒绝原因、引擎错误数。无有效真值的C14不参与码精确率分母；masked/placeholder不当正常有码正例。输入拒绝与OCR失败不混为漏提取；同源重复不抬高样本量。要报告precision/recall时同时列TP/FP/FN、可判定样本数量与来源构成。

若一个码未提取，关联地点的“依赖码失败”和地点提取本身的失败分开记录，避免重复归因。`platform`现有语义未明确前不计算“承运商准确率”；当前回放只忠实保留其输出。

## 分阶段实施与验收证据

1. **先防误码与串配。** 共用规范化、通知块、候选跨度角色核验；修复C09/C20/C21，同时保留C05等正例。给出变更前后同一输入的逐字段差异、拒绝原因和组关联，不以“新增更多结果”验收。
2. **再补地点与隐式句式。** 针对R02/R04/R06/T02及C15/C16补句式、字母码完整边界、中英文标点；至少回归已支持的菜鸟/丰巢/邮政/多码列表。只增加规则能解释的候选，不硬改相似字符。
3. **再处理身份与展示契约。** 共同核对解析、跨图合并、分享唯一性、勾选与保存；C08不能只在解析器里通过。明确旧platform与双角色展示的产品含义；历史记录不自动重写。
4. **用真实截图校准。** 加完整框与候选记录，在受支持iPhone/iOS上非交互可运行层先验证；UI操作和实机交互仍需用户当轮授权或自行观察。冻结版本后用新模板家族留出集评估；未观察到的场景明确不承诺。

这些阶段是后续开发顺序，当前没有实现授权。每阶段只在真实证据驱动下扩展，不用假设的全国模板大全作为完成条件。

Data Correctness Trials：本轮用HCT-2026-09-08-02区分尾号凭证与独立取件码、混合platform与承运商，未默默采纳未知业务定义；HCT-2026-09-08-01要求后续实现保留无文本/无码/部分结果/OCR失败差异。已发现的具体证据是C09/C20错误候选与本机e5rt错误的分离；这不是新实现通过试验，也不是跨任务可靠性已证明。

## 缺口与最小补样

已取得独立公开通知的承运商证据主要是圆通、韵达、邮政；中通有机构模板，顺丰/申通有开源多卡片说明但未取得原图，京东/极兔/德邦尚缺可独立核验的完整真实模板。服务覆盖菜鸟、兔喜、妈妈驿站、丰巢；快宝只到公开格式。超市店名、门牌、自提柜、货架和部分地点已有证据；便利店/门卫室完整真实通知、同一短信多包裹真实原件、重叠截图批次、低清/OCR相似字实图仍不足。

用户后续优先提供：①站名被截短/选成另一个站的截图；②尾号、楼号或其他数字冒充码的例子；③承运商和服务同时出现却对应错误的例子；④两条以上通知或同码不同点的原版式；⑤一个正常识别的对照。每例标明正确码、地点、承运商/服务，未知就写未知。不需要交出全部短信或未脱敏电话/单号；脱敏保留数字长度、角色、分隔符和相对位置。
