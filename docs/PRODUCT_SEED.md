# 收下：极简取件码助手产品 Seed

Date: 2026-07-17

Implementation update: 2026-08-24 已建立 SwiftUI 纵向薄切片，并按“双入口 + 本地交接”模型改造：自己的取件短信通过“信息个人自动化 → 普通快捷指令 → App Intent”自动进入；他人托取的文字或截图通过主动粘贴、本机多图 OCR，或用户明确开启后的前台剪贴板识别进入；需要由他人实际取件时，发送方可把多件待取记录生成本地 `.shouxia` 交接包，接收方预览确认后批量导入。App 不根据 Intent 单次运行伪造自动化已验证状态；首页自动化设置入口可手动隐藏，首次短信来源记录出现后只自动隐藏一次，并可恢复。`1.0` 已在中国大陆 App Store 上架；`1.1.0 (4)` 保留为已完成 TestFlight 真机验收的历史候选。当前 `1.2.0 (5)` 在原生长列表滚动基础上补齐取件现场直接完成、同地点或同批连续取件、取件信息更正、多图去重导入、常用取件点和可选剪贴板自动识别；自动化测试与 Debug/Release 模拟器构建已通过，待真机交互验收。

这是一份产品方向 seed，用于保留关于个人取件码收集、查看和完成体验的讨论，并作为后续 iOS 开发的起点。

产品名称暂定为 **“收下”**。名称、视觉和技术方案仍可调整；当前已确认的是问题、产品原则、第一版闭环和情绪方向。

## 一、讨论起点

日常收到快递取件码后，信息可能散落在：

- 运营商短信；
- 菜鸟、淘宝、京东、拼多多、丰巢等购物或物流 App；
- 他人转发的微信消息；
- 文件传输助手、备忘录等临时存放位置。

任意记事本都能保存取件码，但真正的麻烦不是“没有地方写”，而是：

> 收到信息以后，还需要判断、复制、整理和记住以后去哪里找。

现有物流平台已经覆盖部分包裹，市场上也有取件码管理工具，但用户仍然会把信息随手丢进聊天或备忘录。这说明缺口不只是功能，而是：

> 取件信息没有以足够省事的方式进入一个统一、随时可取用的地方。

## 二、产品定位

“收下”不是物流查询平台，也不是一个专门的记事本。

建议定位：

> **给实际去取快递的人使用的取件码收件箱。**

自己的包裹通常已经由菜鸟、淘宝、京东等平台管理。“收下”最有价值的场景，是把这次真正需要由你去取的信息统一接住：

- 发到这台 iPhone 的自己的取件短信；
- 他人通过聊天发来的取件文字；
- 他人发来的物流截图。

它负责把用户主动交给它的一段取件通知，变成一张清晰、可完成的待取卡片：

```text
复制 / 自动化传入一段通知
    ↓
自动识别取件码与地点
    ↓
进入待取列表
    ↓
到驿站时快速找到
    ↓
取件后“收下”
```

第一阶段仍然是单机个人工具，不提供多人账号或实时同步。这里的“他人托取”包括主动把对方发来的文字或截图交给 App，也包括通过本地交接包把一批待取信息交给实际取件的人；交接包不代表双方状态同步。

## 三、核心理念

一句话理念：

> **自己的自动收，别人托的随手收。**

产品体验由三个情绪阶段组成：

1. **进入时没有负担**：用户不手工建档，不填写表单。
2. **等待时有富足感**：列表像一组正在等待被收下的包裹，而不是令人焦虑的待办事项。
3. **取完时有释放感**：完成动作有克制但令人满足的动画和触觉反馈。

产品不把取件码视为长期信息资产。它只在“包裹已到、尚未取回”的短暂阶段提供价值。

## 四、产品原则

### 4.1 简洁

- 第一版只有一个主页面。
- 打开 App 就看到当前有效的取件码。
- 不默认使用多 Tab、复杂分类、物流时间线或信息流首页。
- 取件码是卡片上最醒目的信息，地点次之，来源和时间弱化。

### 4.2 简单

- 用户提交原始通知，系统负责理解。
- 识别成功后直接保存，不再要求确认每一个字段。
- 只有识别失败或结果明显不完整时才请求修改。
- 不要求用户先配置快递公司、购物平台或复杂规则。

### 4.3 省事

- 添加最多是一次明确动作。
- 查看取件码应在打开 App 后三秒内完成。
- 同一信息重复通过粘贴或短信自动化进入时自动去重。
- 取件后用一次滑动完成，不进入详情页。

### 4.4 不制造压力

- 不使用红色未完成角标、连续催促和任务式警告。
- 不把待取数量写成“还有 5 项未完成”。
- 首页可在数量变化时轮换同一语气下的轻松文案，但不应在普通刷新中跳动。
- 建议文案：
  - “有 5 个包裹在等你”
  - “今天又到了 2 件”
  - “今天的包裹都收下了”

### 4.5 添加安静，完成有仪式感

- 新取件码进入列表时只做轻微出现动画。
- 主要情绪奖励集中在取件完成动作上。
- 动画不能牺牲操作速度，也不能阻断下一次操作。

## 五、暂定名称与语言

产品名暂定：**收下**

建议 App Store 副标题：

> 极简取件码助手

名称能够自然进入产品语言：

- “有 4 个包裹等你收下”
- “添加到收下”
- “收下啦”
- “今天的包裹都收下了”

名称尚未完成 App Store Connect、商标和域名可用性确认，因此仍是工作名称。

## 六、iOS 第一版入口

第一版不追求后台读取全部短信或接入所有购物平台，只提供三个边界明确的入口。

### 6.1 App 内一键粘贴

基础入口：

```text
复制短信或通知
→ 打开“收下”
→ 点击系统粘贴按钮
→ 自动识别并保存
```

实现时应优先使用 iOS 系统提供的 `PasteButton` 或等价的用户主动粘贴能力，避免 App 启动后主动读取剪贴板带来的权限提示和不信任感。

### 6.2 剪贴板读取边界

默认状态只在用户点击系统粘贴按钮时读取剪贴板：

```text
从短信或购物 App 复制完整通知
→ 打开“收下”
→ 点击粘贴按钮
```

用户也可以在“隐私与关于 → 导入设置”明确开启“打开时识别剪贴板”。开启后，App 只在启动或切回前台、并且系统剪贴板的版本发生变化时读取一次；无关文字不会保存，识别到的取件信息仍只在本机处理。该能力默认关闭，不在后台轮询，首次程序化读取时 iOS 可能显示粘贴访问询问。关闭后立即恢复为只响应系统粘贴按钮。

### 6.3 短信自动化与 App Intent

第一版只向系统暴露一个核心动作：

> **保存取件短信（文本）**

该动作接收一段字符串，完成解析、去重和保存，并返回简短结果。它应尽量在后台完成，不要求打开 App。

用户先建立普通快捷指令：

```text
新建“收下自动收码”
→ 从“快捷指令输入”中获取文本
→ 保存取件短信
→ “短信内容”连接上一步的“文本”
```

再建立个人自动化：

```text
底部“自动化” → 右上角“+” → “信息”
→ 发件人保持“任何发件人”
→ “信息包含”设置为“取件”
→ “立即运行”
→ 运行快捷指令
→ 选择“收下自动收码”
```

这条自动化只适用于进入苹果“信息”App 的 SMS/iMessage。用户需要亲自创建一次，App 不能静默创建个人自动化，也不能直接跳转到“自动化”页。底层 App Intent 通过 `AppShortcutsProvider` 注册给系统，但完整正文必须由普通快捷指令明确连接后再传入。只有自动化触发、完整正文传入、后台解析与持久化都得到真机证据，才能称为端到端成功。

### 6.4 第三方通知：明确不支持

iOS 没有让个人自动化在任意第三方 App 通知到达时触发并取得通知正文的通用入口；App Intent 也不能读取通知中心。

因此支付宝、菜鸟、丰巢等 App 通知只支持用户主动复制后在“收下”一键粘贴。手动运行快捷指令再粘贴没有减少步骤，不作为产品入口。完整教训与后续验证顺序见 [`LESSONS.md`](LESSONS.md)。

### 6.5 微信图片与相册 OCR

微信等 App 收到的物流图片可以先保存到相册，再从“收下”的“识别取件截图”入口一次选择最多五张。OCR 使用系统 Vision 框架逐张在本机完成；连续截图中的重复候选按规范化取件码合并，优先保留包含地点、平台或明确标签的结果，再由用户一次确认。单张图片只有一个明确标注结果时仍可直接添加。

图片导入遵循额外的数据最小化边界：不保存原图，不保存完整 OCR 文本，只把取件码、地点、平台与必要的最小文本写入记录，避免把手机号、运单号、商品和门牌详情长期留存在 App 中。同一次确认导入的记录共享一个本地批次标识；即使图片没有识别出地点，也能在取件现场连续查看。用户可配置一个常用取件点为未来缺失地点的新记录补全，界面会明确标注“常用取件点”，修改设置不会回写旧记录。

## 七、第一版数据模型

一条待取记录至少包含：

- 唯一标识；
- 原始文本；
- 取件码；
- 驿站、快递柜或地点；
- 快递公司或来源 App，可为空；
- 地址或货架号，可为空；
- 到达时间；
- 创建来源：粘贴、短信自动化、图片识别；
- 可选的本地导入批次标识，用于缺失地点时连续取件；
- 可选的地点来源：识别、常用取件点或用户更正；
- 状态：待取、已收下、已归档；
- 完成时间；
- 归档时间；
- 用于去重的内容指纹。

第一版解析应优先使用确定性规则和可测试模板，不因为“可以用 AI”而引入云端模型。快递通知通常结构化程度较高，本地处理也更符合隐私预期。

### 7.1 记录与归档生命周期

- 主页面只展示待取包裹，不引入多 Tab。
- 收下后的记录展示录入时间与收下时间。
- “重新设为待取”会把记录恢复到主页面。
- “归档”只整理已收下记录，不删除数据。
- 归档中的记录可以恢复到收下记录。
- 真实删除只在归档页出现，需要二次确认，删除后无法恢复。
- 第一版不增加废纸篓，避免“归档”和“删除”之间再出现一层含混状态。

## 八、主页面

第一版建议只有一个主列表：

```text
有 4 个包裹在等你

┌──────────────────┐
│ 菜鸟驿站 · 北门       │
│                      │
│      3-2-4012        │
│                      │
│ 今天 14:32            │
└──────────────────┘

┌──────────────────┐
│ 丰巢 · 1号柜           │
│                      │
│       829146         │
└──────────────────┘
```

视觉方向：

- 卡片像柔和的包裹标签或票券，而不是工作任务。
- 多张卡片可以有轻微层叠或厚度感，但不能影响快速扫描。
- 不靠堆砌装饰制造富足感，而是让每张卡片都像“已经属于你、正在等你收下的东西”。
- 需要同时覆盖无记录、单条记录、多条记录、超长取件码和地点缺失等状态。

## 九、“收下”完成动画

暂定采用“卡片折成包裹并收进家里”的方向。

### 9.1 触发

- 用户向右完整滑动卡片，或点击无障碍等价操作。
- 使用系统列表滑动动作处理方向判断和完成阈值，避免与纵向滚动争抢；完成后仍保留明确反馈。

### 9.2 动画过程

1. 系统滑动动作确认完成，避免与纵向滚动争抢。
2. 卡片在约 460ms 内轻微下沉、缩小并淡出，不模拟实体折叠或收纳。
3. 其他卡片使用自然的弹簧动画补位。
4. 显示“轻轻收下了”和约五秒撤销入口。

### 9.3 体验约束

- 动画要短、顺滑、可连续触发。
- 不使用大面积彩带或每次都播放声音。
- 触觉反馈遵循系统设置，不覆盖静音和辅助功能偏好。
- 动画结束后保留约五秒“撤销”入口，避免误操作。
- 撤销不应阻断动画，用户先得到完成感，再拥有纠错能力。
- 开启“减少动态效果”时提供简化的淡出和列表补位版本。

## 十、第一版明确不做

- 不做用户账号和服务端同步。
- 不做家庭、夫妻或宿舍共享。
- 不直接接入淘宝、京东、拼多多等订单 API。
- 不做完整物流查询和运输时间线。
- 不在 1.0 预设数据分析和统计；等真实使用后再决定哪些指标有价值。
- 不读取全部短信历史。
- 不做聊天机器人或 AI 对话。
- 不做广告、商城、优惠券和导购。
- 不先做 Android 版本。
- 不为了展示技术而引入云端大模型。

这些方向不是永久排除，而是在个人 iOS 闭环成立前不进入首版。

## 十一、首个验收闭环

第一版成功不以功能数量衡量，而以一个真实动作是否足够省事衡量：

> 一条真实取件短信通过“收到信息”自动化加入，或一条购物 App 通知通过主动粘贴加入；App 正确提取取件码与地点；到驿站后三秒内找到；取件后用一次滑动完成，并获得令人满足的“收下”反馈。

建议使用真实短信样本验证：

- 菜鸟驿站；
- 丰巢或其他快递柜；
- 快递超市或小区物业；
- 含货架号的通知；
- 只有取件码、没有明确地点的通知；
- 同一包裹重复通知；
- 他人通过微信转发的通知。

首轮可量化标准：

- 常见真实样本识别成功率达到 80% 以上；
- 重复导入不会生成重复卡片；
- 短信入口无需逐条复制；购物 App 通知不超过一次复制加一次粘贴；
- 打开 App 后三秒内能找到所需取件码；
- 完成动画不阻塞连续操作；
- 原始消息和解析结果默认只保存在本机。

## 十二、主要风险

### 12.1 入口仍然不够省事

如果用户的取件信息主要来自支付宝等第三方通知，当前入口仍然不够省事。一键粘贴只是可用入口，不是长期优势；在没有新的系统或平台数据入口前，不应包装成自动收码。

### 12.2 现有平台已覆盖大部分包裹

菜鸟等平台已经能够关联手机号和亲友包裹。产品必须证明跨来源统一、极简展示和完成体验带来的价值，而不能只依赖“现有平台没有这个按钮”。

### 12.3 产品过薄

取件码是高频但生命周期很短的信息。第一版可以是优秀的个人工具，但商业价值尚未验证。不能因为体验讨喜就提前推断付费意愿。

### 12.4 情绪设计变成装饰

富足感和解压动画必须服务于核心动作。若动画降低查码速度、遮挡内容或长期使用后令人厌烦，应优先保留效率和克制。

## 十三、后续开发顺序

建议下一轮只做规格和技术验证，不立刻扩展完整产品：

1. 收集并脱敏 20–50 条真实取件通知样本。
2. 定义解析结果和去重规则。
3. 建立 SwiftUI 本地原型：待取列表、一键粘贴、完成和撤销。
4. 实现唯一的 App Intent：保存取件短信。
5. 在真机验证短信自动化完整正文、后台运行和去重边界；Share Extension 保留为后续候选。
6. 做“收下”动画的三种时长与触觉强度原型，选择最克制但最满足的一版。
7. 自用两周，再决定是否加入小组件、锁屏展示和家庭共享。

## 十四、下一轮关键问题

- 第一版最低支持哪个 iOS 版本？
- 原始通知是否永久保留，还是取件后一段时间自动删除？
- 用户是否需要手动编辑识别结果？编辑入口应有多深？
- 首版是否必须包含桌面或锁屏小组件？
- 完成动画在不引入实体容器后，是否仍能传达“事情已经安稳收好”？
- “收下”是否可以通过 App Store Connect 和商标可用性检查？
