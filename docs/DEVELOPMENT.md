# 收下开发与验证

## 当前实现

首个纵向薄切片已经包含：

- SwiftUI 单页待取列表；
- 系统 `PasteButton` 主动粘贴，以及默认关闭、由用户在导入设置中开启的前台剪贴板自动识别；
- 系统照片选择器与本机 Vision OCR，支持他人通过微信等来源发来的物流截图；
- 一次选择最多五张图片，逐张 OCR 后按取件码跨图去重；单图只有一个明确标签结果时直接添加，其他情况统一勾选确认；
- 图片导入只持久化取件码、地点、平台和必要片段，不保存原图、手机号、运单号或 OCR 全文；
- 同次图片确认导入共享批次标识；没有地点时仍可进入同一取件组；
- 导入设置可配置只作用于未来记录的常用取件点，使用时在卡片与大字模式标注来源；
- 本地确定性解析，提取取件码、地点和来源平台；
- 基于规范化原文 SHA-256 与当前待取码的双层重复导入保护；
- 本地 JSON 持久化；
- 首页会在待取数量变化时，从空状态或有包裹状态的独立文案池中稳定随机一组文案；
- 轻点待取卡片进入取件现场大字模式，同一地点或同批导入多件可左右切换；
- 在取件现场直接“已取到，收下”，同组有下一件时自动切换，最后一件完成后返回首页；
- 从取件现场更正取件码和地点，空地点可稍后补充；
- 系统列表向右全滑“收下”、简化完成动画和五秒撤销；
- 带录入时间和收下时间的记录页；
- 记录可重新设为待取；默认最近 30 天，可切换全部，包含旧归档记录；
- 收下记录可二次确认后永久删除；待取记录不能通过此入口删除，不设置废纸篓；
- “保存取件短信”App Intent，可接收“信息”个人自动化传入的短信正文并在后台导入；
- 首页“自己的取件短信，自动收好”入口与两阶段引导，可打开“快捷指令”App，并分别说明普通快捷指令和个人自动化；
- 通过 `AppShortcutsProvider` 将“保存取件短信”可靠注册到快捷指令动作库；普通快捷指令必须把“快捷指令输入”转换为文本并连接到该动作的“短信内容”；
- 不根据 App Intent 单次运行声称自动化已验证，因为 App 无法判断它是自动触发还是手动运行；
- 首页自动化入口可手动隐藏；首次出现短信自动化来源记录后只自动隐藏一次，并可从“设置 → 导入设置”恢复；
- 待取记录可批量生成本地 `.shouxia` 交接包；接收方打开后预览确认，再以“他人托取”来源批量导入；
- 系统分享成功结束后，发送方所选记录离开待取列表，在收下记录中标记为“交给别人”；取消分享不改变记录；
- 交接包只包含取件码、地点、平台和用于重复导入保护的记录标识，不包含短信原文、手机号、运单号或商品信息；
- 菜鸟、丰巢、京东、邮政、快递超市等样本测试。

## 双入口产品模型

```text
自己的快递
→ 信息个人自动化
→ 普通快捷指令“收下自动收码”
→ 保存取件短信 App Intent

他人托取的快递
→ 粘贴取件文字 / 识别取件截图
→ 同一个 PickupRepository

请他人代取
→ 选择多件待取记录
→ 发送本地“收下交接包”
→ 发送方完成交接并退出待取
→ 对方预览确认
→ 同一个 PickupRepository
```

产品表达是“自己的自动收，别人托的随手收”。三种技术入口仍然存在，但用户不需要理解内部技术分类。

## 四个实现入口

### 1. 短信个人自动化

App 暴露一个接收字符串的“保存取件短信”App Intent。已经获得真机证据的可靠路径包含两段，不能省略普通快捷指令：

```text
第一段：新建普通快捷指令“收下自动收码”
→ 从“快捷指令输入”中获取文本
→ 添加“保存取件短信”
→ 将“短信内容”连接到上一步输出的“文本”

第二段：快捷指令底部“自动化” → 右上角“+” → 信息
→ “发件人”保持“任何发件人”
→ “信息包含”设置为“取件”
→ 选择“立即运行”
→ 运行快捷指令
→ 选择“收下自动收码”
→ 保存
```

Apple 当前文档确认“信息”触发器可按发送人和“信息包含”过滤，并支持自动运行。App 不能静默创建、修改或查询个人自动化。普通快捷指令可以通过 iCloud 分享链接降低接线成本，但链接和导入行为仍必须经过空白设备真机验证。

首页初始提供“自己的取件短信，自动收好”卡片。用户可以主动隐藏；首次出现短信自动化来源记录后，App 只自动隐藏一次，之后尊重用户从“设置 → 导入设置”恢复入口的选择。没有真实 iCloud 分享链接时，按钮只打开“快捷指令”App并展示完整手动说明；不能提交占位链接。`AppShortcutsProvider` 只负责让系统发现底层动作，不会创建普通快捷指令或个人自动化。入口隐藏不代表 App 声称自动化已配置或已验证；用户仍需用第一条真实短信端到端确认。

### 2. 粘贴与可选自动识别

默认路径是用户从他人的聊天或其他 App 复制完整取件信息，打开“收下”并点击系统 `PasteButton`。该操作表达明确的粘贴意图，不需要 App 预先读取剪贴板。

“设置 → 导入设置”还提供默认关闭的“打开时识别剪贴板”。开启后，App 在启动或切回前台时先比较 `UIPasteboard.changeCount`，只有变化时才尝试读取一次；自动路径只接受与“取件码、提货码、领取码”等标签直接关联的代码，不使用任意数字兜底。解析失败与无关文字保持安静且不持久化，成功导入才显示提示。最后处理的变化计数保存在 `AppStorage`，避免同一剪贴板反复触发。iOS 可能在程序化读取时显示系统粘贴访问询问，App 不绕过该权限，也不在后台轮询。

系统 `PasteButton` 表达了明确的用户意图，因此手动路径继续接受独立的 4 至 8 位数字或完整取件通知。所有文字、图片、短信自动化与交接导入先按完整原文指纹去重，再对当前仍待取的记录按规范化取件码去重；记录完成后，未来包裹仍可复用相同短码。

第三方 App 通知不是自动化入口。App 不会、也不能读取支付宝、菜鸟、丰巢或其他 App 在通知中心中的内容。手动运行快捷指令后再粘贴，与 App 内一键粘贴相比没有价值，不作为产品路径。

### 3. 普通文字与收下交接包

`1.2.3 (13)` 本地开发版新增普通文字模式：“请人帮取”默认选中第一项“收下交接包”，第二项“普通文字”将所选记录按地点整理，支持预览与复制，用户自行粘贴到聊天。接收方不需要安装 App。文字复制不触发记录交接或完成；确认取到后由用户手动收下。缺失地点写明待确认，常用取件点保留来源提示。详见 [普通文字分享](PLAIN_TEXT_SHARING.md)。

默认的“收下交接包”继续使用原流程：

待取列表非空时，首页提供“请人帮取”。发送方选择一项或多项待取记录后，App 通过系统分享面板发送 `.shouxia` 文件。系统分享动作成功结束后，发送方所选记录以“交给别人”完成本侧流程并离开待取；取消分享不改变记录。这个完成只表达责任已经交出，不声称对方已经导入或取到。交接包是发送时的本地快照，不建立账号、云同步、回执或双方完成状态联动。

接收方点开文件后，App 先校验版本、数量、字段长度和取件码格式，再展示全部内容。只有用户点击确认后才批量写入 `PickupRepository`。同一来源记录重复出现在交接包中时，以源记录标识生成的交接指纹去重。

### 4. 相册图片识别

用户可以把微信等 App 收到的物流图片保存到系统相册，打开“收下”后点击“识别取件截图”，并在系统照片选择器中一次选择最多五张。App 逐张使用 Apple Vision 的准确模式在本机识别简体中文与英文，不上传图片，也不申请整库照片访问。

识别器优先查找“取件码、取货码、提货码、领取码”等标签附近的数字和字母组合，避免把运单号、手机号、距离、时间和门牌号当作取件码。多图候选按规范化取件码合并，优先保留地点、平台与标签更完整的候选。只有单张图片的一个明确标签结果直接添加；多图、多个结果或只有无标签候选时，先让用户勾选确认。

持久化前会构造只包含取件码、地点和平台的最小文本。原图、OCR 全文、手机号、运单号与商品信息不会写入本地记录。同次确认导入的记录共享 `importBatchID`；如果 OCR 没有地点，可使用用户设置的常用取件点补全并标为 `commonDefault`，从而与识别地点和用户更正区分。

## 工程结构

```text
Shouxia/
  App/              App 入口
  Features/
    Inbox/          首页、情绪文案与待取卡片
    Handoff/        发送、接收与系统分享交接包
    ImageImport/    图片候选确认
    Settings/       关于、导入设置与自动化引导
    PickupMode/     取件大字模式与编辑
    History/        历史记录
    PickupStore     共享界面状态
    ShouxiaTheme    视觉变量与通用样式
  Models/           取件记录和导入结果
  Services/         解析器与本地持久化
  Intents/          系统“保存取件短信”动作
ShouxiaTests/   解析与去重测试
```

UI、剪贴板、图片识别和短信 App Intent 共用同一个 `PickupRepository`，避免不同入口产生不同的解析和去重行为。

## 正式视觉与完成交互

正式页面采用“晚风杏桃”方向：天空浅蓝画布与两处低对比环境光提供呼吸感，云白纸面承接信息，杏桃色集中承担包裹与完成温度，薄荷色只负责行动和微风提示。完整的变量、品牌资产、组件、关键状态和动效节拍保存在 [Figma v2](https://www.figma.com/design/fjQN8yRyNkYPqMUcL9I6B2)。

首页使用 SwiftUI `List` 与系统 `swipeActions` 统一处理纵向滚动和向右全滑“收下”，不再在整张卡片上叠加自定义 `DragGesture`。系统确认完成后，纸签在约 460ms 内向下移动 10pt、缩小至 0.98 并淡出，随后列表自然补位并显示“轻轻收下了”和五秒撤销入口。开启“减少动态效果”时只播放约 160ms 的短淡出，不播放位移或缩放；VoiceOver 用户可通过卡片的“收下”自定义动作完成同一操作。

Figma 执行环境中的 SF Pro Rounded 会产生零宽文字，因此设计稿用 Noto Sans SC 作为可见字体桥接；真实 App 仍由 SwiftUI 系统圆体与中文系统回退字体渲染，字体正确性以模拟器和真机为准。

Logo、App Icon、空状态与完成提示统一使用“杏桃包裹 + 云白取件卡”标志，避免用不符合真实包裹尺度的口袋隐喻；可编辑 SVG 源文件保存在 `docs/brand/`。历史记录页继续复用同一组颜色和文字层级。此前的 Debug Design Lab 已在方案迁移后移除，正式工程只保留一套界面。
