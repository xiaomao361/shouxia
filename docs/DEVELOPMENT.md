# 收下开发与验证

## 当前实现

首个纵向薄切片已经包含：

- SwiftUI 单页待取列表；
- 用户主动点击的“粘贴取件信息”按钮，只在点击后读取他人或其他 App 发来的取件文字；
- 系统照片选择器与本机 Vision OCR，支持他人通过微信等来源发来的物流截图；
- 图片只有一个明确标签结果时直接添加；多个或无标签候选进入勾选确认；
- 图片导入只持久化取件码、地点、平台和必要片段，不保存原图、手机号、运单号或 OCR 全文；
- 本地确定性解析，提取取件码、地点和来源平台；
- 基于规范化原文 SHA-256 的重复导入保护；
- 本地 JSON 持久化；
- 首页会在待取数量变化时，从空状态或有包裹状态的独立文案池中稳定随机一组文案；
- 轻点待取卡片进入取件现场大字模式，同一地点多件可左右切换；
- 向右滑动“收下”、简化完成动画和五秒撤销；
- 带录入时间和收下时间的记录页；
- 记录可重新设为待取或归档，归档可恢复；
- 只有归档页允许二次确认后永久删除，不设置废纸篓；
- “保存取件短信”App Intent，可接收“信息”个人自动化传入的短信正文并在后台导入；
- 首页“自己的取件短信，自动收好”入口与两阶段引导，可打开“快捷指令”App，并分别说明普通快捷指令和个人自动化；
- 通过 `AppShortcutsProvider` 将“保存取件短信”可靠注册到快捷指令动作库；普通快捷指令必须把“快捷指令输入”转换为文本并连接到该动作的“短信内容”；
- 不根据 App Intent 单次运行声称自动化已验证，因为 App 无法判断它是自动触发还是手动运行；
- 首页自动化入口可手动隐藏；首次出现短信自动化来源记录后只自动隐藏一次，并可从“隐私与关于”恢复；
- 待取记录可批量生成本地 `.shouxia` 交接包；接收方打开后预览确认，再以“他人托取”来源批量导入；
- 交接包只包含取件码、地点、平台和用于重复导入保护的记录标识，不包含短信原文、手机号、运单号或商品信息；
- 菜鸟、丰巢、京东、邮政、快递超市等样本测试。

## 双入口产品模型

```text
自己的快递
→ 信息个人自动化
→ 普通快捷指令“收下自动收码”
→ 保存取件短信 App Intent

他人托取的快递
→ 粘贴取件文字 / 识别取件截图
→ 同一个 PickupRepository

请他人代取
→ 选择多件待取记录
→ 发送本地“收下交接包”
→ 对方预览确认
→ 同一个 PickupRepository
```

产品表达是“自己的自动收，别人托的随手收”。三种技术入口仍然存在，但用户不需要理解内部技术分类。

## 四个实现入口

### 1. 短信个人自动化

App 暴露一个接收字符串的“保存取件短信”App Intent。已经获得真机证据的可靠路径包含两段，不能省略普通快捷指令：

```text
第一段：新建普通快捷指令“收下自动收码”
→ 从“快捷指令输入”中获取文本
→ 添加“保存取件短信”
→ 将“短信内容”连接到上一步输出的“文本”

第二段：快捷指令底部“自动化” → 右上角“+” → 信息
→ “发件人”保持“任何发件人”
→ “信息包含”设置为“取件”
→ 选择“立即运行”
→ 运行快捷指令
→ 选择“收下自动收码”
→ 保存
```

Apple 当前文档确认“信息”触发器可按发送人和“信息包含”过滤，并支持自动运行。App 不能静默创建、修改或查询个人自动化。普通快捷指令可以通过 iCloud 分享链接降低接线成本，但链接和导入行为仍必须经过空白设备真机验证。

首页初始提供“自己的取件短信，自动收好”卡片。用户可以主动隐藏；首次出现短信自动化来源记录后，App 只自动隐藏一次，之后尊重用户从“隐私与关于”恢复入口的选择。没有真实 iCloud 分享链接时，按钮只打开“快捷指令”App并展示完整手动说明；不能提交占位链接。`AppShortcutsProvider` 只负责让系统发现底层动作，不会创建普通快捷指令或个人自动化。入口隐藏不代表 App 声称自动化已配置或已验证；用户仍需用第一条真实短信端到端确认。

### 2. 用户主动粘贴

用户从他人的聊天或其他 App 复制完整取件信息，打开“收下”并点击“粘贴取件信息”。读取必须由用户点击主操作按钮触发；App 不在启动、切回前台或后台时主动读取剪贴板。

第三方 App 通知不是自动化入口。App 不会、也不能读取支付宝、菜鸟、丰巢或其他 App 在通知中心中的内容。手动运行快捷指令后再粘贴，与 App 内一键粘贴相比没有价值，不作为产品路径。

### 3. 收下交接包

待取列表非空时，首页提供“请人帮取”。发送方选择一项或多项待取记录后，App 通过系统分享面板发送 `.shouxia` 文件。交接包是发送时的本地快照，不建立账号、云同步或双方完成状态联动；系统分享完成也不会自动删除或完成发送方记录。

接收方点开文件后，App 先校验版本、数量、字段长度和取件码格式，再展示全部内容。只有用户点击确认后才批量写入 `PickupRepository`。同一来源记录重复出现在交接包中时，以源记录标识生成的交接指纹去重。

### 4. 相册图片识别

用户可以把微信等 App 收到的物流图片保存到系统相册，打开“收下”后点击“识别取件截图”，并在系统照片选择器中选择该图。App 使用 Apple Vision 的准确模式在本机识别简体中文与英文，不上传图片，也不申请整库照片访问。

识别器优先查找“取件码、取货码、提货码、领取码”等标签附近的数字和字母组合，避免把运单号、手机号、距离、时间和门牌号当作取件码。只有一个明确标签结果时直接添加；识别到多个结果或只有无标签候选时，先让用户勾选确认。

持久化前会构造只包含取件码、地点和平台的最小文本。原图、OCR 全文、手机号、运单号与商品信息不会写入本地记录。

## 工程结构

```text
Shouxia/
  App/          App 入口
  Features/     主列表与页面状态
  Models/       取件记录和导入结果
  Services/     解析器与本地持久化
  Intents/      系统“保存取件短信”动作
ShouxiaTests/   解析与去重测试
```

UI、剪贴板、图片识别和短信 App Intent 共用同一个 `PickupRepository`，避免不同入口产生不同的解析和去重行为。

## 正式视觉与完成交互

正式页面采用“晚风杏桃”方向：天空浅蓝画布与两处低对比环境光提供呼吸感，云白纸面承接信息，杏桃色集中承担包裹与完成温度，薄荷色只负责行动和微风提示。完整的变量、品牌资产、组件、关键状态和动效节拍保存在 [Figma v2](https://www.figma.com/design/fjQN8yRyNkYPqMUcL9I6B2)。

待取卡片支持直接向右拖动。越过阈值时先给出触感与薄荷柔光确认；松手后纸签在约 460ms 内轻抬、缩小并向右下归位，随后列表自然补位并显示“轻轻收下了”和五秒撤销入口。开启“减少动态效果”时改为短淡出，不播放位移、缩放或旋转过程；VoiceOver 用户可通过卡片的“收下”自定义动作完成同一操作。

Figma 执行环境中的 SF Pro Rounded 会产生零宽文字，因此设计稿用 Noto Sans SC 作为可见字体桥接；真实 App 仍由 SwiftUI 系统圆体与中文系统回退字体渲染，字体正确性以模拟器和真机为准。

Logo、App Icon、空状态与完成提示统一使用“杏桃包裹 + 云白取件卡”标志，避免用不符合真实包裹尺度的口袋隐喻；可编辑 SVG 源文件保存在 `docs/brand/`。记录与归档页继续复用同一组颜色和文字层级。此前的 Debug Design Lab 已在方案迁移后移除，正式工程只保留一套界面。

## App Store 1.0 准备

当前已提交构建为 `1.0.0 (1)`；本轮目标是将双入口与正确自动化引导改造为 `1.0.0 (2)` 并先进入 TestFlight。项目使用 iPhone-only 配置、工具类别、无透明通道的 1024 × 1024 App Icon，并在生成的 Info.plist 中声明不使用非豁免加密。`Shouxia/Resources/PrivacyInfo.xcprivacy` 声明当前版本不跟踪、不收集数据，也不连接跟踪域名。

App 内“隐私与关于”页面说明本地处理、主动剪贴板读取和短信个人自动化边界。App Store Connect 元数据、隐私政策、支持页、审核说明与提交检查表位于 `docs/app-store/`。真实用户 TestFlight 验收完成前，不重新提交正式 App Review。
