# 本地识别机制

## 架构

文字、短信自动化、文字分享和图片识别复用 `Shared/PickupRecognitionCore.swift`。图片由 Apple Vision 提供文本行及位置信息，规则在本机提取取件码、地点和快递信息；规则随应用更新，不下载远程配置。

识别依次进行规范化、通知分段、候选收集、数字用途分类、候选关系处理与入口投影。候选保留命中规则、规范化 UTF-16 范围、决策及原因，供诊断回放使用；应用不额外持久化诊断原文。

## 候选与用途

标签、凭码领取句式及明确取件上下文提供候选依据。手机号、尾号、运单号、日期、时间、门牌和数量需要按其用途判断；数字形状相符不能单独证明是取件码。

- 明确遮挡或截断的码不作为完整码保存，不截取可用前缀。
- 码中保留字母、前导零及分段，不全局替换 `O/0` 或 `I/1`。
- 更正或替代关系使旧码失效时，保留该关系；新码不可用时不能继续保存旧码。
- 地点、日期或营业时间的修改不作为取件码替换。
- 同行收件人、地址和电话号码只影响对应字段范围，不排除整行的有效取件码。

## 结果状态

| 状态 | 含义 |
| --- | --- |
| 可用 | 满足当前入口的保存条件 |
| 需核对 | 存在可处理候选，但需用户确认或更正 |
| 排除 | 有明确其他用途、被替代或不满足完整码条件 |
| 未处理通知 | 通知中有缺失、遮挡或不可用项，保留完整性提示 |

`requiresReview` 与 `Notification.unresolved` 分别表示可核对候选和未处理项。用户更正候选后，不应残留重复的未识别提示。直接文字与自动路径跳过需核对项并保留部分结果提示；图片与分享路径交由核对模型处理。

普通候选可默认选中，低置信度或缺地点保留提示；截断、备选码、用途冲突及冲突地点需明确处理。OCR 置信度描述字符识别，不等于业务语义正确概率。

## 字段关联与去重

字段在各自通知内关联，缺失地点不借用另一条通知补全。当前 `platform` 是兼容的快递/取件服务展示字段，不能一律解释为承运商；地点来源区分识别、常用默认与用户更正。

候选合并和待取去重结合取件码、地点及快递信息。同码不同地点、上下文不足或关系冲突时，不直接视为重复。存储与分享约定见[功能与数据约定](PRODUCT.md)。

## 回归与诊断

```sh
bash scripts/check_recognition.sh /tmp/shouxia-recognition-check
bash scripts/replay_pickup_samples.sh docs/recognition/1.2.9/contracts.jsonl
```

固定验收分别断言结果状态、码、地点、平台、核对与遗漏数量，失败返回非零退出码。诊断回放输出候选与排除原因，不直接更新预期值。

数据集包括[研究样本](research/2026-10-15-pickup-parsing/README.md)、历史缺陷输入、关系约束与构造格式变体，索引见[识别数据](recognition/README.md)。这些输入已参与开发，不能用通过数量推算未知模板或真实用户准确率；图片标注行回放也不证明真实 OCR 正确。

新增真实样本应先独立标注码、地点、角色与不可判定字段，再比较逐字段结果。样本用于规则调整后归入回归集，不再作为未见模板验证。历史验证文件按记录的源码哈希和环境解读。
